## IDの考え方
### システム内部で使うID
システム内部で利用する主キーは、固定長にする必要はない。
例
```text
1
2
3
4
5
```
または
```text
BIGINT
AUTO_INCREMENT
```
など。
#### 理由
- 一意に識別できる
- JOINしやすい
- DBで扱いやすい
- 採番ルールを考えなくてよい
---
### 利用者が見る番号
利用者向けの番号は固定長にすることが多い。
例
```text
USR000001
USR000002
```
```text
S000001
```
```text
R202608280001
```
など。
#### 理由
- 人が扱いやすい
- 帳票に載せやすい
- 電話で伝えやすい
- 桁数が揃う
---
### 実務でよくある構成
内部で利用するIDと、利用者へ表示する番号を分ける。
例
```text
account_id
---------
1
display_no
---------
USR000001
```

### 上長からの指摘について
業務システムでは、
```text
会員番号
社員番号
予約番号
```
などを固定長で管理することが多い。
ただし、それは利用者向けの管理番号であり、
必ずしも主キーを固定長にするという意味ではない。

---
### 今回の音楽教室システムの場合
現在の
```text
アカウントID
```
は
- 生徒情報
- 講師・スタッフ情報
- レッスンスケジュール
などを関連付けるための内部キーである。
そのため、
```text
1
2
3
100
101
```
のような連番でも問題ない。

---
### 今回の学習での方針
```text
アカウントID
→ int の連番
（必要になったら追加）
生徒番号
講師番号
予約番号
→ 固定長コード
```
とする。
