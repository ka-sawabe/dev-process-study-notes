## G021 空き枠選択画面

#### 1、画面の目的を確認
+ 目的：予約可能なレッスン枠を探せること。
↓
#### 2、業務ルールを確認
+ 生徒ごとに楽器コース、担当講師は固定。
+ 1回30分。月4回まで受講可能。
↓
#### 3、利用者の操作シナリオを考える
+ ユーザは空いてるレッスン枠（日付・時間）を探したい、ということだけ。
  →そのため、検索項目の入力欄と検索結果を表示するのではなく、
  初期表示で検索結果をカレンダーUIに表示してそこから選択するUIとする。

+ 次回予約日時が設定済み or 今月の受講回数 >= 4の場合はカレンダーの枠が選択不可として、
  次画面へ遷移できないようにした方がシンプルで、
  業務ルールを画面項目へ落とし込めていて分かりやすい。

## G030 レッスン枠登録画面

#### 1、画面の目的を確認
+ 目的：講師・スタッフが使用。
+ 講師の予定（レッスン可能な日付・開始時間・終了時間）を登録および公開できること。
  
#### 2、業務ルールを確認
+ 1回30分。
+ レッスン可能時間は11:00～21:00。定休日は不定休。曜日は考慮しなくて良い。レッスン可能な日は講師による。

#### 3、利用者の操作シナリオを考える
+ 講師が日付を選択。レッスンができる時間を範囲指定する。
 （営業時間があるので、日付またぐのは考慮せず、日付を一日選択して時間は範囲指定のほうが良いはず。）
 　↓
+ 公開すると、空き枠選択画面でその範囲が30分単位で○が表示される。 

**※公開ボタンは必要か？**
+ 今回は登録する＝公開とする。
【理由】
今回のスコープでは変更・キャンセルは考慮しない。
したがって
- 下書き保存
- 公開停止
- レッスン枠変更
- レッスン枠削除
も考慮していないため。

G031[登録する]⇒G032登録完了の流れで問題なし。公開ボタンは不要。

## G090 ユーザー登録画面

#### 1、画面の目的を確認
+ アプリでログイン・予約するために必要な情報をこの画面で登録する

※今回は、
+ アプリでログイン・予約をするために最低限必要な情報のみを登録する方針とする。
+ 会員情報の詳細管理（住所、生年月日、保護者情報など）は❌スコープ外とする。

#### 2、業務ルールを確認
+ 生徒ごとに楽器コース、担当講師が固定。

+ 予約受付は対面、電話、メールで行う
  ⇒そのため、利用者への連絡手段としてメールアドレスと電話番号が必要。
  対面・電話でも受け付けるので、講師・スタッフは生徒のユーザ登録も行える必要がある。

+ 当教室のコース：ピアノ、ギター、ボーカル、フルート、サックス 
  ⇒一人の講師で複数コース担当することも考慮する 

#### 3、利用者の操作シナリオを考える 
以下を登録したい。

登録するのは以下の4パターン。
+ 生徒のユーザー情報の登録（本人による登録）
+ 生徒のユーザー情報の登録（講師・スタッフによる代理登録）
+ 講師のユーザー情報の登録
+ スタッフのユーザー情報の登録

登録したい情報は以下。
（生徒の場合）
+ 利用者区分
+ ユーザーID（今回はメールアドレスとする。）
+ パスワード
+ 氏名
+ 電話番号
+ 担当講師（楽器コース名）

（講師の場合）
+ 利用者区分
+ ユーザーID（今回はメールアドレスとする。）
+ パスワード
+ 氏名
+ 電話番号
+ 担当楽器コース(担当のコースをすべて選択できる形式にする)
  
（スタッフの場合）
+ 利用者区分
+ ユーザーID（今回はメールアドレスとする。）
+ パスワード
+ 氏名
+ 電話番号

### 補足

#### １、登録したのが生徒なのか講師・スタッフなのかをどうやって判断するのか？ 

まず、登録対象が生徒・講師・スタッフのどれであるかを識別する仕組みが必要。

##### 案1
生徒用ユーザー登録と講師・スタッフ登録画面　で2つに分ける。
画面ID・URLも別にする
 
こちらでも問題ない。 
メリット
+ 分かりやすい。項目定義がシンプル。
デメリット
+ 画面、遷移、ワイヤーフレーム、テストが増える。

⇒今回は採用しない。

##### 案2
 
ユーザー登録画面は生徒用・講師用・スタッフ用　は共通にする。
 
メリット
- 画面数が増えない。
- 保守がしやすい。

デメリット
- 利用者区分による表示条件が増える。

⇒こちらを採用。

例
生徒の場合：
ログイン画面の「新規登録はこちら」から遷移
⇒ユーザー登録画面
※利用者区分は画面には表示しない。
　区分は生徒に固定。区分はhiddenにする。

講師・スタッフの場合：
管理者から招待メールを送付する。
⇒招待URLから遷移
⇒ユーザー登録画面

利用者区分（生徒・講師・スタッフ）をラジオボタンで表示する。

遷移元またはURLから利用者区分を判定し、 利用者区分に応じてユーザー登録画面の表示項目を切り替える。


#### ２、生徒の楽器コース、担当講師はいつ設定するか？

実際の運用としては、
+ 体験レッスン⇒入会⇒担当講師決定⇒ユーザー登録⇒初回のレッスンの予約
+ 体験レッスン⇒担当講師決定⇒入会⇒ユーザー登録⇒初回のレッスンの予約
のどちらかを想定しているため、
ユーザー登録するときには、担当の講師が決まってる。

以下の2パターンを検討。
##### 案1
G021 空き枠選択画面で毎回選択する。
- 担当講師・楽器コースを選択
- 空き枠を表示

これでも問題ない。
ただし、予約のたびに同じ担当講師を選択する必要があり、操作が増える。⇒今回は採用しない。

##### 案2（採用）
G090 ユーザー登録画面で設定する。
- 楽器コース
- 担当講師
をユーザー登録時に入力する。

登録後は空き枠選択には担当講師はラベルで固定表示できる。
予約時は担当講師の空き枠のみ表示する。

毎回講師を選択する手間がなくなり、利用者の操作が減る。⇒こちらを採用。

#### ３、楽器コース、担当講師は誰が設定する？** 
本来はスタッフが設定する運用も考えられる。

ただし今回は、以下は❌スコープ外とする。考慮しない。
+ 詳細な会員情報の管理機能
+ 後から担当講師を変更する機能
ただし、生徒の代理登録は考慮する。

そのため、

生徒本人が登録する場合
講師・スタッフが代理登録する場合
のどちらでも、

ユーザー登録画面で担当講師・楽器コースを設定できるものとする。  

⇒案2のユーザー登録画面で楽器、担当講師を入力する方式を採用。

例えばホットペッパービューティーなど、利用者が自分で担当美容師選んで予約するケースは一般的であり、案2の運用でも不自然ではないと判断。
